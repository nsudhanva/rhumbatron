# Rhumbatron UX research

> **Status:** Reference only. The redesign in this document was tried on 2026-10-09. The owner rejected it, and commit `c34c9e8` reverted it. The original UI stays.

**Date:** 2026-10-09
**Scope:** `apps/web` (the TanStack Start UI at `dev.rhumbatron.com`). No app code was changed for this research.
**Question from the owner:** "Is this application UI/UX friendly for developers? I am as developer as anyone can get but this UI/UX is still hard for me to understand. How can we make this more friendly for developers, product managers, and users? I'd like to reverse the complex animations/DAG etc. stuff we have built and the design."
**Short answer:** No. The UI shows how Rhumbatron works inside, not what the user needs to know or do next. Keep the data. Change the default view to a plain status page with one timeline and one button, and move the machinery to an Advanced area.

### 1.2 Top 10 changes (priority order)

| # | Change | Fixes problems | Details |
|---|---|---|---|
| 1 | **Rebuild the Change page as a status page.** One headline (`[icon] Word · sentence`), one primary button, and a 5-step vertical timeline: Planned -> Agents working -> Checks -> Your approval -> Shipped. Put approval and shipping on this page as one action, "Approve and ship". | 1, 2, 6 | 7.4, 7.5 |
| 2 | **Move the machinery out of the default view.** Remove the activity player, Work Graph DAG, stat strips, the duplicate conflict block and the candidate table from the Change page. Keep them in "Debug view" (today's Flight Control) under a collapsed Advanced nav group. | 2, 4 | 5.3, Appendix B |
| 3 | **Apply the glossary everywhere.** Release 1842, Version A/B, Code change, Approach, Checks, Ship, Out of date, Set aside, Needs your approval. Internal names stay in tooltips, Technical details and Advanced pages. `lib/glossary.ts` already holds the labels. | 3, 8 | 7.6, Appendix A |
| 4 | **Show the code.** Add a "Files changed (N)" tab with `+a −d` per file and a real diff on click. Show "4 files changed +120 −8" on each task row. This needs one API addition: store the patch when a code change is published. | 5 | 7.4 tabs, B.4 |
| 5 | **Show the outcome where people look.** "Shipped" step with "Release 1842 is live" and **Open app**. Overview header "Live: Release 1842 · shipped 2h ago". A "Releases" list that maps each release to its goal and files. | 6 | 7.3, 7.4 step 5 |
| 6 | **Put the composer first on the Overview.** Empty textarea with the demo goal as placeholder, then "Needs you", then in-progress cards, then recent changes. Replace the raw event log with plain Activity sentences. | 7 | 7.3 |
| 7 | **Never leave the user stuck between steps.** When all tasks are done and no version exists, the primary button is "Run checks". Later, compose versions automatically. | 1 | 7.4 status table |
| 8 | **One status vocabulary.** Icon + word + one sentence per state, from one shared component. "Needs your approval", "Not run" (amber, never green), "Set aside", "Out of date". | 8 | 7.4, 8.4 |
| 9 | **Simplify navigation.** Projects; per project: Overview, Activity, Costs; Advanced (collapsed): Agents, All checks, Code, Product map, Event log, Debug view. Remove the Product/Systems toggle and the unbuilt items. | 9 | 7.1 |
| 10 | **Apply the v2 visual system.** 14px body, 12px floor, sentence case, weight 600, 6px/8px radius, 1px borders, a blue accent separate from danger red, one standard spinner. | 10 | 8 |

Changes 1-3 give most of the value. Do them first, in one release, because they share the Change page. Changes 4 and 5 need small API work (B.4). Changes 6-10 are independent and can run in parallel.

### 1.3 What to keep

The UI has real strengths. Keep them through the redesign:

- Status is always a word, not color alone (`components/ui/status-pill.tsx:12`).
- A missing check is never green: `not_checked` maps to an amber state (`components/ui/status-pill.tsx:55`). This matches AGENTS.md 34.4.1.
- The notification inbox already groups "Needs you" above "Updates" (`components/notifications/notification-inbox.tsx:151-152`).
- Empty states say what is missing and how to fix it (`components/ui/empty-state`, for example `routes/projects.$projectId.tsx:196-199`).
- Section errors have a Retry button (`routes/projects.$projectId.tsx:189-194`).
- Reduced motion is respected (`theme.css:624, 723`). There is a skip link (`components/shell/app-shell.tsx:66-71`) and polite live regions (`components/agents/agent-activity.tsx:205-207`).
- Every fact on screen comes from recorded data, not estimates (`routes/projects.$projectId.tsx:266-270`).

## 2. Method

### 2.1 Inputs

| Input | How it was used |
|---|---|
| `AGENTS.md` sections 3, 4, 38, 39, 55 | Product intent, controlled vocabulary, required pages, demo runbook. |
| `apps/web/src/routes/*` (19 route files) and `components/*` (about 34,000 lines in total) | Primary evidence. Each route was read top to bottom. Large components were read in full or searched for every visible string. |
| `apps/web/src/theme.css` | Type, radius, weight, motion tokens. |
| `workers/api/src/notifications.ts` | Where notification links go. |
| Live dev site `https://dev.rhumbatron.com` (host from `infrastructure/terraform/envs/dev/main.tf:6`) | Fetched with `curl` on 2026-10-09: `/`, `/projects/acme-shop`, `/sign-in`, plus `https://api-dev.rhumbatron.com/health` and `/v1/projects`. |
| Comparable products | See section 6 and 2.4. |

### 2.2 Live-site result

- All three pages returned HTTP 200 with server-rendered HTML. API health returned `{"service":"rhumbatron-api-dev","environment":"dev","ok":true}`.
- Clerk auth blocks every data page. `/v1/projects` returned `401 {"error":{"code":"unauthorized","message":"Missing session token"}}`. Signed-out pages show "Sign in to see your projects." or "Sign in to view this project."
- Therefore every signed-in finding comes from source. The signed-out shell was checked live. It shows the full 12-item project nav (2 tagged "soon", the rest disabled), the Product/Systems toggle, the color-mode toggle, the tagline "Many agents can propose many futures. Only verified evidence can advance the canonical state." and a status bar "live off · env dev · rhumbatron-web-dev". That is the first impression for a new user.

### 2.3 Procedures

1. **Heuristic evaluation (section 3).** One evaluator applied Nielsen's 10 heuristics to every route. Each finding has a `file:line` reference and a severity on Nielsen's scale: 4 = blocks the task, 3 = major, 2 = minor, 1 = cosmetic.
2. **Cognitive walkthrough (section 4).** Three personas, one task each. For each step: the action, what the UI shows (from source), the friction, and a severity. A step "fails" when the UI cannot answer the persona's question at all.
3. **Jargon count (section 5.1).** A throwaway script (not committed) follows the relative imports from each route file, takes string literals and JSX text, drops class-name strings, and matches 36 groups of internal terms (for example "Candidate", "ChangeSet", "Intent", "Canonical", "Generation/S-number", "Claim", "Gate", "Woken/asleep"). The shared status-pill vocabulary and the shell are excluded so that each count shows the page's own words. The count is an upper bound: it includes text for states that a user sees only sometimes. The Change page was also counted by hand for one demo state.
4. **Motion and visualization inventory (section 5.3, Appendix B).** Every `@keyframes` in `theme.css`, every `rh-*` motion class, every xyflow canvas and every heat grid, traced to the component that uses it.

### 2.4 Comparable-product research (sections 6-8)

- **Checked on the web (2026-10-09):** GitHub Copilot coding agent sessions (docs.github.com), GitHub status check states (docs.github.com), Railway deployment states (docs.railway.com), Devin session tools (docs.devin.ai). Codex, Cursor and Jules from secondary sources only.
- **From product knowledge, not re-checked in a browser:** the GitHub PR merge box and Checks tab, the GitHub Actions run view, the Vercel deployment page, Linear, Render, CircleCI, and type and radius sizes. Treat exact pixel values as close approximations. Check them against the live products before treating them as specifications.
- **Contrast values in 8.5** were computed with a script from the hex values (WCAG 2.x relative luminance).

### 2.5 Limits

- No usability test with real users. The walkthroughs are expert predictions. Validate the top 3 changes with 3-5 people per persona before and after.
- No signed-in screenshots. A logged-in browser session was not available to this research.
- Data-dependent states (for example two versions plus a conflict) were traced in code, not seen live.

Check (Evidence) words: `pass` + `checked_supported` = **Passed**; `fail` = **Failed**; `error` = **Couldn't run**; `skipped` = **Skipped**; `not_checked` = **Not run** (amber, never green); `checked_no_signal` = **No result**.

#### Step 1: Planned

- Collapsed line: "Split into {n} tasks · {risk} risk" plus duration.
- Expanded:
  - "Done when" (`acceptanceCriteria`) as a checklist.
  - "Must not change" (`invariants`) with a lock icon.
  - "Tasks" as an **ordered list**, not a DAG. Order is topological from `dependsOn`. Each row: status icon, `title`, and "after {dependency title}" when the task waits.
  - Link: "Show as graph" (Advanced, opens the Debug view DAG).
- While compiling: "Splitting your goal into tasks..." with a spinner. No skeleton graph.

#### Step 2: Agents working

- Collapsed line: "{done} of {total} tasks done · {active} agents working".
- Expanded: one row per task, ordered with running first, then waiting, then done.

| Task state | Row text (plain) | Source |
|---|---|---|
| running | **{title}**. Under it: "Reading src/wishlist/api.ts · for 1m 12s". Then "Approach: {Intent.summary}" and "Will touch 3 files" (opens the `expectedFiles` list). | `RunProgress.lastStep` through `describeStep()`, `startedAt`/`progressAt`, `TaskRun.outcome` (Intent) |
| assigned | "Starting: the agent is reading the task." | `TaskDetail.status` |
| pending / ready | "Waiting for '{dependency title}'" / "Ready, starts soon." | `dependsOn` |
| completed | "Done · 4 files changed +120 −8". Expands to the per-file list and a "Approach: ..." line. | `WorkspaceFork.changeSet.fileStats/insertions/deletions` |
| failed, retrying | "Attempt 1 failed: {failureReason}. Retrying with a stronger model." | `TaskRun.failureKind`, next run `tier` |
| failed | "Failed: {failureReason}" with the "Details" disclosure. | `TaskRun` |

- "Technical details" disclosure per row: model (Claude Haiku/Sonnet/Opus), model calls n/cap, tokens, cost, attempt, decided by (rules or Clef).
- **Conflict callout** (inside step 2, amber, only when a `ConflictDetail` is not `resolved`):
  - Title: "Two agents chose different approaches for {area}."
  - Body: Approach A: {intents[0].summary}. Approach B: {intents[1].summary}.
  - Footer: "Rhumbatron will build both versions and keep the one that passes the checks." (when `forkDecision.kind === "fork"`).
  - "Why they conflict" opens `signals[].detail` and `assumptions`.
  - Claims, challenge IDs, and severity names are not shown.

#### Step 3: Checks

With one version, it shows a list of checks. Each row has an icon + plain title (titles in `candidate/model.ts`: Build, Project tests, API contract, Protected Cart invariant, Performance, Security, Browser flow) + `EvidenceRecord.summary` + duration + a "Details" link. Details shows stdout and screenshots from `/evidence/...`. A failed row opens on its own. `not_checked` rows say "Not run: {gap reason}" in amber.

With two or more versions:

- A **result sentence** goes first: "Version B passed all 7 required checks. Version A was set aside: API response time p95 was 240 ms (limit 200 ms)."
- Two compact cards follow, one per version: "Passed 7 of 7" / "Failed 1 of 7", the failing check named, and "+412 −37 in 9 files".
- Link: "Compare versions in detail" (`/compare/$changeId`).
- Required checks met counts only `pass` + `checked_supported`, matching the release gate.

#### Step 4: Your approval

- Not required: a grey line "No approval needed for {risk} risk changes." The step shows as skipped (MinusCircle).
- Required and pending: an amber box.
  - Title: "Needs your approval."
  - Reason: "This change touches sharing permissions (high risk). Policy {policy} needs a person to approve."
  - "You are approving: Version B · 7 of 7 checks passed · 9 files changed · Preview".
  - Primary: **Review and approve**. The dialog repeats the summary, offers an optional reason, and has the buttons **Approve and ship** / **Reject**.
- Granted: "Approved by {approverName} · {timeAgo}" and the reason if given.
- Rejected: "Rejected by {name}: {reason}". The Change does not ship.

#### Step 5: Shipped

- Not yet: grey "Not yet."
- Promoting or releasing: "Shipping Release {g+1}..." with a spinner. Sub-lines come from `build.*` / `deployment.*` feed events when present: "Build started", "Deploying".
- Done: "Release {g} is live." with **Open app**, plus "Release {g-1} -> Release {g}" and the source commit (`PromotionOutcome.sourceCommit`) under "Technical details".
- Release failed: "Release {g} was saved but did not deploy. Your previous app is still live." Primary: **See details**.

#### Tabs other than Progress

- **Files changed** (count): the union of files across the winning version's code changes. Each row shows path and `+adds −dels`, and the diff opens on click when a diff source exists. Grouping by task is optional.
- **Checks** (count): every check for every version, with filters (Passed / Failed / Not run).
- **Activity**: `FeedEvent.summary` as plain past-tense sentences grouped by minute ("Agent started on 'Add wishlist API'", "Version B passed Performance"). Raw event types appear only in the Event log (Advanced).

Remove from the default Change page: the `AgentActivity` git-lane view, the stat strip (`ChangeStats`), the xyflow Work Graph with its "Task details" inspector, the candidate table with "Gate / Promotable" columns, the "Open Flight Control" primary button, and the `Live` pill (replaced by the "Updating live" text in meta).

### 7.5 Exactly one primary action: rules

1. The primary button exists only when the user can move the Change forward: Run checks, Review and approve, Ship Release N, Open app, Raise budget, Start again.
2. Everything else is secondary (outline) or sits in the `...` menu: Compare versions, Debug view, Copy ID, Reject.
3. The header button and the active timeline step show the **same** action, so the button never conflicts with the step.
4. In waiting states the header shows no button. A notification ("Needs your approval") brings the user back when needed.

## 8. Visual direction (design v2 proposal)

Direction: calm, neutral, legible. Light by default, dark kept. One brand color (blue) for primary action, links, focus, and "in progress". Red is used only for danger. Cards have 1px borders and 8px radius. There are no 2px rules, no uppercase kickers, and no text below 12px.

### 8.1 What changes in `apps/web/src/theme.css`

1. **@theme radius:** remove the zero-radius block and the global `border-radius: 0 !important` rule in `@layer base`.
2. **@theme shadows:** small shadows return as a soft card shadow (values in 8.2).
3. **Font:** see 8.3.
4. **Palette:** replace values in place (8.2). Same token names, so most components change without edits.
5. **Decouple danger from the accent.** Today `--color-kumo-danger`, `--color-kumo-danger-tint`, `--text-color-kumo-danger` and `--color-kumo-badge-red` point at `--rh-accent-*`.
